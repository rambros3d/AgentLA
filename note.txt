TEST-HARNESS BUGS FOUND + FIXED (test/test_stm32f1_heartbeat_debug.py)
--------------------------------------------------------------------------------
1. send_cmd() always waited the FULL timeout (5 s) per command instead of
   returning when the response arrived. 39 writes + 39 verifies x 5.3 s
   ≈ 414 s > the 400 s test timeout -> test appeared to "hang" mid-verify.
   The probe itself was always fast (~50 ms response); this was a host-side
   harness bug. FIXED: early-exit on terminal OK/ERR line + short idle grace.

2. After the early-exit fix it surfaced that the probe streams "OK DEBUG REGS"
   FIRST and the 17 register lines AFTER. FIXED with the idle-grace window.

3. Memory-mutation parse bug: got = int(l.split('0x', 2)[1].split('=')[0], 16)
   parsed the ADDRESS (0x20000000) instead of the read-back VALUE, so the test
   reported a mismatch even though the probe wrote and read back the marker
   correctly. FIXED: parse the value after '='.

4. test_bluepill_flash.py is a LEGACY UART-bootloader script (uses the removed
   "MODE PROG ON" command) - superseded by the SWD flasher. Not a regression.

Result: heartbeat test stages 1-3 now pass (connect, flash+verify, halt/step/
regs/memory mutation). Stage 4/5 still fails (see OPEN ISSUE 2).

--------------------------------------------------------------------------------
OPEN ISSUE 2: NO TARGET CPU RESET IN THE HEARTBEAT TEST (root cause of stage 4/5)
--------------------------------------------------------------------------------
Root cause: the heartbeat test flashes the firmware but never resets the target.
It erases/writes flash while the OLD firmware is still executing from that very
flash -> the CPU faults (stage-3 register dump shows PC=0xFFFFFFFE = lockup,
garbage R7-R12, LR=0xFFFFFFF1). Stage 4's DEBUG RUN resumes dead code, so the
LA never sees the PC13 double-pulse (captured line is mostly HIGH with
single-sample glitches).

Fix implemented (firmware): new "DEBUG RESET" command in main.c cmd_debug() -
pulses nRST (GPIO6) low 20 ms, releases, does an SWD line reset + full
target_detect() re-connect, then waits 100 ms for boot.
- Build clean, flashed, command responds "OK DEBUG RESET", SWD re-connects
  afterwards (IDCODE works).
- PROBLEM: the reset does NOT appear to actually reboot the CPU - after
  DEBUG RESET + HALT the register dump still shows PC=0xFFFFFFFE (same lockup
  values). Possibilities: (a) nRST wiring GPIO6<->BluePill nRST not connected,
  (b) nRST pulse not effective, (c) reconnect sequence re-faults. UNRESOLVED.
- Also observed: DEBUG HALT became nondeterministic after DEBUG RESET
  (OK once, ERR once) - the post-reset reconnect state needs hardening.
